# Doklo 개발자 프리뷰

지원되는 앱 코드를 읽어 기능 문서 초안을 만들고 사람이 검토하는 로컬 도구입니다. Apache-2.0 CLI, 검토용 웹 UI, 읽기 전용 MCP 서버를 제공합니다.

## 설치

```bash
npm install -g @mayp/doklo
```

0.4.1은 Node.js 20.9 이상이 필요하며 작업 공간당 프로젝트 하나를 지원합니다.

## 프로젝트에서 시작하기

```bash
doklo init
doklo generate
doklo serve --open
doklo sync --check
```

초기화가 모델·브랜치 선택을 기록하고 프로젝트를 스캔한 뒤 다음 명령을 안내합니다. 생성 전에 전송할 소스와 모델 경로를 확인해 주세요. 선택한 소스 발췌가 해당 모델 공급자에게 전송될 수 있으며 모델 이용 비용은 별도입니다. 생성 결과는 초안이고, 사람이 로컬 웹에서 검토한 뒤 active로 전환합니다.

명령 옵션은 `doklo --help` 또는 `doklo <command> --help`로 확인할 수 있습니다. 에이전트는 프로젝트 루트를 명시해 `doklo mcp`로 연결합니다. 설치 패키지의 `AGENT_GUIDE.md`에 에이전트 안내가 포함됩니다.

## 지원 기능

- **범용 소스 분석:** 전용 파서나 package.json 없이 읽을 수 있는 UTF-8 소스를 묶어 모델 검토에 전달합니다. Next.js App Router는 전용 파서로 라우트와 의존성 정보를 보강하며, 다른 프레임워크는 범용 소스 근거를 사용합니다.
- **소스 제외 처리:** 알려진 민감 경로·Git 제외 파일·의존성·빌드 산출물은 소스를 읽기 전에 제외합니다. 바이너리·UTF-8이 아닌 파일·1 MiB 초과 파일도 제외합니다.
- **변경 감지와 편집 보호:** `doklo sync --check`는 추적 중인 소스의 변경을 알려 줍니다. 일반 `doklo sync`는 사람이 편집한 문서를 건너뛰어 보존합니다.

## 변경 이력 남기기

설명마다 Dok 파일(`_meta.history`)에 변경 이력이 남고, 저장소와 함께 버전 관리됩니다. Doklo는 사람이 Studio에서 작업할 때만 이력 항목을 추가하며, `doklo generate`와 `doklo sync`는 항목을 쓰지 않습니다. 항목에는 날짜가 들어가고, `DOKLO_AUTHOR` 환경 변수나 git `user.name`이 있으면 작성자 이름도 함께 기록됩니다.

- **다시 생성하면 제안이 붙습니다.** `doklo sync`가 이미 있는 설명을 다시 생성하면 그 설명은 `draft`로 돌아가고, 무엇이 바뀌었는지 요약한 제안이 붙습니다(예: `Updated the description; added 2 steps.`). 이 요약은 모델이 쓴 글이 아니라 규칙에 따른 비교 결과입니다. 이름 변경과 설명·단계·규칙·확인 기준의 변화를 알려 주고, 내용이 같으면 아무것도 붙이지 않습니다. `doklo sync --judge`는 그 대신 판사가 쓴 문장을 붙일 수 있습니다(다음 절 참고). 제안은 아직 이력이 아니며 어떤 Live Doc에도 나오지 않습니다.
- **승인하면 기록됩니다.** Studio는 제안을 `Proposed: …`로 보여 줍니다. 설명을 하나씩 또는 한꺼번에 `active`로 바꾸면 제안이 이력에 기록되고 사라집니다.
- **노트와 상태 변경도 기록됩니다.** `What changed? (optional)`에 적은 노트는 저장할 때 기록되며, 분류를 따로 고르지 않으면 Changed로 들어갑니다. `active`로 바꾸면서 노트를 적으면 제안 대신 노트가 기록됩니다. `active`·`deprecated`·`archived` 전환 같은 상태 변경은 노트 없이도 기록되지만, 본문 편집은 노트를 적었을 때만 기록됩니다.

설명을 하나씩 또는 한꺼번에 승인해도 `doklo sync`의 재생성 대상에서 빠지지 않습니다. 코드가 바뀌면 설명은 `draft`로 돌아가고, 승인할 새 제안이 붙습니다. `--force` 없이 실행하면 `doklo sync`는 Studio에서 본문을 고쳤거나, 상태를 planned·deprecated·archived로 바꾸거나 거기서 되돌린 설명을 건너뜁니다. `--force`를 붙이면 그 설명도 새 초안으로 다시 생성하며, 고친 내용은 덮어씁니다. 이전 버전의 Doklo에서 승인한 설명에는 아직 편집 표시가 남아 있어서, 코드 변경으로 처음 낡았을 때 한 번은 `doklo sync --force`가 필요합니다. 실제로 고친 설명을 건드리지 않으려면 `doklo sync --dok <ID> --force`로 하나씩 실행하세요. 그 뒤로는 `--force` 없이 이 흐름이 이어집니다. 0.3.2 이전 방식으로 추적하던 설명은 `unknown`으로 표시되고 stale이 되지 않습니다. 먼저 `doklo scan --repair-tracking`으로 추적 정보를 다시 구성하세요. 복구한 설명은 검토가 필요한 stale로 표시되어 다음 `doklo sync`가 다시 생성합니다(편집 표시가 남은 설명은 `--force`가 필요합니다). 비교 요약 대신 직접 쓴 문장을 붙이려면 다음처럼 실행합니다:

```bash
# 이번 실행에서 다시 생성되는 모든 설명에 붙습니다. --category는 --note와 함께만 쓰고,
# --note는 --check와 함께 쓸 수 없습니다.
doklo sync --note "기프트 카드 결제 추가" --category added
```

`keep-a-changelog`는 포함된 active 설명의 기록된 변경을 날짜와 Keep a Changelog 분류별로 묶습니다. 처음 `active`가 된 설명은 Added 분류에 나오고, 기록이 없는 설명은 나오지 않습니다. `release-digest`는 직전 렌더 이후 추적하는 소스가 바뀐 설명만 변경으로 분류하고, 그런 설명에는 그 뒤 기록된 노트와 승인된 제안을 적으며, 기록이 없으면 일반 문구를 씁니다. MCP 툴은 이력을 반환하지 않습니다.

## 무엇을 다시 만들지 판사에게 맡기기

코드가 바뀌었다고 설명이 모두 틀리게 되지는 않습니다. 두 가지 검사가 상관없는 변경 때문에 설명이 `draft`로 돌아가는 일을 막습니다.

**모양만 바뀐 변경은 drift가 아닙니다.** 설명이 추적하는 JavaScript·TypeScript 파일에서 주석·공백·줄바꿈 방식만 바뀌었다면 그 설명은 stale이 아닙니다. 따로 켤 것이 없고, 모델 호출이나 비용도 없습니다. `doklo sync`는 모양만 바뀐 설명의 수를 알려 주고, `doklo show <ID>`는 최신 여부 줄에 그렇게 적으며, MCP는 `is_stale: false`를 반환합니다. 그 밖의 파일과 파싱되지 않는 파일은 지금처럼 바이트 단위로 비교합니다.

**다시 생성하기 전에 판사에게 묻기.** 그래도 stale인 설명은 `doklo sync --judge`로 다시 생성하기 전에 아직 맞는지 모델에게 먼저 물을 수 있습니다.

```bash
doklo sync --judge                 # stale인 설명마다 먼저 묻습니다
doklo sync --judge --judge-max 10  # 최대 10개만 묻고, 나머지는 평소처럼 다시 생성합니다
```

판사는 설명 본문, 그 설명을 생성한 커밋 이후 추적 파일에서 바뀐 부분(git diff, 믿을 수 있는 diff를 만들 수 없으면 파일 전체), 설명의 소스 앵커를 읽습니다. 검사 한 번에 최대 240,000자입니다. 자격 증명처럼 Doklo가 모델에 보내지 않는 파일은 이름만 알리고 내용은 보내지 않습니다. 답은 셋 중 하나입니다.

- **그대로 맞음:** 다시 생성하지 않고 상태도 그대로 둡니다. 판정은 `.doklo/cache/judge/`에 저장되어, 코드·기준 커밋·본문이 그대로인 동안 다음 `doklo sync --judge`가 다시 묻지 않고 씁니다.
- **고쳐야 함:** 다시 생성하고, 설명이 이제 무엇을 말해야 하는지 판사가 쓴 한 문장을 승인 때 기록될 변경 제안으로 붙입니다. `--note`나 아직 승인하지 않은 직접 쓴 제안이 있으면 그쪽이 우선합니다. 다시 생성한 결과가 이전과 같으면 제안을 붙이지 않고, 직접 고칠 수 있게 그 설명을 알려 줍니다.
- **정하지 못함:** `--judge` 없이 실행한 것처럼 다시 생성합니다. 호출 실패, 정해진 형식이 아닌 답, 받지 않은 파일을 근거로 든 답, 근거 없이 그대로 맞다고 한 답도 정하지 못함으로 봅니다.

판정은 근거가 붙은 의견일 뿐 승인이 아닙니다. 판사는 작업 공간의 기본 언어로 씁니다(`ko`면 한국어, 그 밖에는 영어). `doklo sync --judge`는 동의를 두 번 받습니다. 먼저 판사 호출, 그다음 여전히 필요한 재생성이며, `--yes`는 둘 다 동의합니다. `--check`는 모델을 부르지 않으므로 `--judge`와 함께 쓸 수 없습니다.

**판사 모델.** 판사는 재생성 모델의 공급자를 따릅니다. Anthropic API 키를 쓰면 Claude Sonnet 5(기본값), ChatGPT(Codex) 로그인을 쓰면 GPT-6 Luna입니다. 하나로 고정하려면 `doklo model --task judge --set anthropic/claude-sonnet-5` 또는 `doklo model --task judge --set openai/gpt-6-luna`를 실행합니다. 다른 모델은 받지 않습니다. GPT-6 Luna는 OpenAI API 키(`doklo auth --provider openai`의 API 키 방식 또는 `OPENAI_API_KEY`)로도 판사를 맡습니다. 그렇게 쓰려면 두 번째 명령으로 고정합니다. 생성은 OpenAI API 키로 실행되지 않으므로 기본값은 ChatGPT 로그인에서만 GPT-6 Luna를 고릅니다. API 키로 하는 호출은 `store: false`로 보냅니다. 저희 벤치마크에서 두 모델 모두 고쳐야 할 변경을 놓치지 않았습니다. GPT-6 Luna는 훨씬 싸고 빨랐지만 관련 없는 설명에 몇 번 잘못된 경보를 냈고 실행마다 판정이 일부 달랐으며, Sonnet 5는 잘못된 경보를 내지 않았습니다. 벤치마크는 GPT-6 Luna를 ChatGPT(Codex) 로그인으로 쟀고, API 키 엔드포인트는 스모크 테스트만 했습니다.

**비용.** 검사 한 번에 보내는 양은 재생성 한 번과 비슷하고, 사용한 토큰은 생성과 같은 한도(`DOKLO_MAX_TOKENS_PER_RUN`, `DOKLO_MAX_TOKENS_TOTAL`)에 포함됩니다. 고쳐야 하는 설명은 검사와 재생성 비용을 모두 냅니다. 판사가 줄이는 것은 모델 비용이 아니라 검토할 일입니다.

**판사가 남긴 설명 확인하기.** 판사가 그대로 맞다고 한 설명은 사람이 web에서 **Still accurate**(한국어 화면에서는 **여전히 맞다**)로 확인할 때까지 stale로 남습니다. 그동안 `doklo sync --check`는 판사가 그대로 맞다고 했지만 아직 확인 전이라는 표시와 함께 그 설명을 계속 나열하고 종료 코드 1을 내며, `doklo show <ID>`도 같은 표시를 하고, MCP는 계속 `is_stale: true`를 반환합니다. 그 설명을 남긴 `doklo sync --judge` 실행은 partial(종료 코드 1)로 끝납니다. 확인은 본문과 상태를 바꾸지 않고 이력 항목도 쓰지 않으며, 확인한 뒤에는 추적 파일이 다시 바뀔 때까지 최신으로 읽힙니다. `--judge` 없이 `doklo sync`를 실행하면 그 설명도 다시 생성합니다.

**제약.**

- 두 검사에는 생성이 이제 함께 기록하는 사실이 필요합니다. 모양만 바뀐 변경 검사에는 정규화 해시가, 판사에는 파일별 해시와 기준 커밋이 필요하므로 판사는 git 저장소에서만 동작합니다. 이전 버전의 Doklo로 생성한 설명에는 이 사실이 없어서, 한 번 다시 생성될 때까지 모양만 바뀌어도 stale이 되고 `--judge`도 묻지 않고 재생성으로 보냅니다.
- 0.3.2로 올린 뒤 `unknown`으로 표시되는 설명은 stale이 되지 않습니다. `doklo scan --repair-tracking`으로 추적 정보를 다시 구성하세요.
- 사람이 고친 설명은 지금처럼 `--force` 없이는 건너뜁니다.
- draft 설명, 추적 파일이 없어졌거나 읽을 수 없는 설명, 추적 정보를 복구한 설명은 판사 없이 다시 생성합니다. `--judge-max`를 넘거나, 240,000자 입력 한도를 넘거나, 판사에게 보여 줄 수 있는 변경이 없는 설명도 마찬가지입니다.

## 0.4.1 문서 언어

Dok을 영어, 한국어, 일본어, 중국어 간체·번체, 프랑스어, 스페인어, 독일어, 포르투갈어(`en`, `ko`, `ja`, `zh-Hans`, `zh-Hant`, `fr`, `es`, `de`, `pt`)로 쓸 수 있습니다. `doklo init`은 코드에서 언어를 제안합니다. i18n 설정, 방문자가 읽는 화면 글, 메시지 파일이 하나뿐일 때 그 언어, `<html lang>` 순으로 보고, 코드에 단서가 없으면 CLI 언어를 제안합니다. `--default-locale`로 직접 고를 수 있으며 `ko_KR`, `zh-TW`처럼 적은 태그는 표준 형태로 저장합니다. `doklo scan --json`은 서비스마다 감지한 언어를 알려 줍니다.

Dok마다 쓰인 언어를 기록합니다(`_meta.locale`). 언어를 바꾸려면 `workspace.json`의 `default_locale`을 고치고 다시 생성하십시오.

소스가 다른 언어로 쓰여 있어도 Dok의 언어는 바뀌지 않습니다. 화면 문구는 이미 Dok의 언어일 때만 그대로 인용하고, 그렇지 않으면 뜻을 쓰고 원문을 괄호로 한 번 덧붙입니다. 그래도 다른 문자 체계로 쓰인 Dok은 저장하지 않습니다. 한 번 다시 시도한 뒤 `DOK_LANGUAGE_MISMATCH`와 다시 생성할 명령을 알려 줍니다.

한국어 고객 문장은 항상 합쇼체(`formal`)로 씁니다. `doklo init`은 더 이상 묻지 않으며, `--korean-tone`은 받아들이되 경고만 하고 무시합니다. 해라체가 필요한 작업 공간은 `workspace.json`에 `korean_customer_tone: plain`을 적습니다.

sync 판사와 Live Docs 템플릿은 여전히 영어나 한국어로 씁니다.

## 0.3.2 Live Docs 개선

도움말의 읽기 화면과 목차를 개선했으며, 여러 도움말을 한 화면에 넣어도
각 목차가 해당 문서의 항목으로 이동합니다. 긴 입력에서 문구 검사가 오래
걸리던 문제를 수정하고, 렌더러가 이전 문서 상태를 받아 변경 내용을 비교할
수 있게 했습니다. 실험 단계인 HWPX 도구는 선택 설치로 유지합니다.
기존 문서를 자동으로 다시 쓰거나 승인하지 않습니다.

## 0.3.1 실행 전 계획과 도움말 통합

- `init --code-root web`으로 작업 공간 안의 서비스 디렉터리를 선택합니다.
  스캔 결과에서 분석 방식·포함 소스 경로·제외 범위를 확인할 수 있습니다.
- 유료 실행 전 `generate --dry-run` 또는 `consolidate --dry-run`으로 소스
  후보를 확인합니다. 계획 없음과 실제 0건을 구분하고, 토큰 추정치와 출력
  상한을 분리하며, 이후 취소·실패에도 공급자가 보고한 사용량을 보존합니다.
  추정치는 공급자의 요금을 보장하지 않습니다.
- `--var html_fragment=true`, `--var heading_level=2`로 정제된 도움말 HTML
  조각을 만듭니다. 필요하면 고유한 `--var id_prefix=sidebar`를 지정하십시오.
  앱의 스타일을 적용하고 출력은 작업 공간 안에 보관합니다.
- 새 기본 역할 이름은 작업 공간 언어를 따르고 기존 편집 이름은 보존합니다.
  생성에는 확정 용어와 공통 한국어 문체 정책(`formal` 합쇼체, 또는
  `workspace.json`에 적은 `plain` 해라체)을 사용합니다. 정식 한국어 도움말 출력은 명확한 문체 충돌이나
  검토하지 않은 정책 변경을 알리고 중단합니다. 원문을 교정·검토하거나 초안
  미리보기로 확인하십시오. 기존 문구를 자동으로 다시 쓰지 않습니다.
- WebP 등 공개 이미지 포맷 이름의 식별자 오탐을 줄였습니다. 내부 Dok ID와
  다른 고객 문구 검사는 유지합니다.

생성 문서는 여전히 사람이 검토해야 합니다. 사용 예시·용어 검토·출력 전달
절차는 [최초 실행과 도움말 통합 안내](https://github.com/mayp-ai/doklo/blob/v0.3.1/docs/ko/first-run-and-embedding.md)를 참고하십시오.

## 0.3.0 생성 복구와 초안 미리보기

JSON 형식 오류나 잘린 모델 응답은 기본적으로 한 번 재시도합니다.
`--retries 0`으로 끄거나 `--retries 2`로 추가 시도를 최대 두 번까지 지정할 수
있습니다. 재시도도 실행 동의·토큰 한도에 포함되며 공급자 비용이 늘어날 수
있습니다. 일부 문서가 최종 실패하면 실패 종료 코드와 해당 Dok 목록을 제공합니다.

```bash
doklo generate --only CHAT
doklo live-docs render help-page --dok CHAT --format html --preview
```

`--only`로 복구 대상을 제한합니다. 기존 문서는 명시적으로 `--force`를 쓰지
않으면 건너뛰며, 재생성에 실패하면 원본을 보존합니다. 안정화된 Markdown/HTML
미리보기는 Hub의 draft 상태를 유지하고 미검토 초안 표시를 붙입니다.
고객 문구 검사는 유지되며, 미리보기 출력은 저장된 Publication의 정식 발행
근거로 사용할 수 없습니다.

새 스캔·통합에서는 보조 파일만 있는 기능 후보를 제외하고 Next.js 화면 간
공용 함수의 근거 범위를 좁힙니다. 기존 캐시에 적용하려면 `doklo scan`과
`doklo consolidate`를 다시 실행해야 하며, 통합에는 모델 비용이 들 수 있습니다.
기존 Hub 문서를 자동으로 다시 쓰거나 삭제하지 않습니다. 제품 설명은 의도이며
구현의 증명이 아닙니다. 모델이 기록한 내용 검토 의견은 사람이 확인해야 합니다.

## 기존 문서의 추적 복구

이전 방식으로 추적 정보를 만든 문서는 `unknown`으로 표시됩니다. 다음 명령으로 소스 추적 정보를 다시 구성할 수 있습니다.

```bash
doklo scan --repair-tracking
```

복구 과정에서 기존 문서의 본문과 이력은 유지합니다. 복구 후에도 문서 검토가 필요하며, 추적 정보를 고쳤다고 문서 내용의 정확성이 보증되는 것은 아닙니다.

## 현재 제약

- 프레임워크 감지와 범용 소스 분석이 모든 경로나 동작의 추출을 보장하지는 않습니다.
- 경로 규칙은 임의의 이름을 가진 일반 소스 안의 비밀값까지 판별하지 못합니다. 해당 파일은 분석 전에 `.gitignore`로 제외하십시오. 파일을 추가한 뒤에는 다시 스캔해야 합니다.
- 기능 하나의 소스 본문이 192,000자를 넘으면 생성 전에 중단합니다. 내용을 자르지 않으므로 큰 서비스나 생성 묶음은 나눠야 합니다.
- 전용 파서의 정적 import 추적에는 깊이 제한이 있습니다. 동적 import·런타임 연결은 누락될 수 있습니다. 미해결 내부 import는 스캔을 중단합니다.
- fresh는 추적 소스 해시가 같다는 뜻으로 문서 정확성·완전성을 보증하지 않습니다.
- **`doklo sync --force`는 사람이 편집한 문서를 다시 생성해 편집 내용을 덮어씁니다. 수동 편집 내용을 자동으로 병합하지 않습니다.**
- 키 없는 Claude Code 경로는 generate에만 제공됩니다. sync에서도 지원한다고 가정하거나 공급자를 임의로 바꾸지 마세요.
- 로컬 Live Review 연동은 이번 프리뷰에 포함되지 않습니다. Dok 초안을 검토하는 로컬 웹 UI는 `doklo serve --open`으로 사용할 수 있습니다.
