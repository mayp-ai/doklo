# 생성 복구와 초안 검토

소스 경로 선택, 사전 토큰 추정, 정본 용어, HTML fragment와 출력 위치는 [실행 범위 확인과 앱 도움말 통합](first-run-and-embedding.md)을 참고하세요.

이 가이드는 현재 소스의 동작을 설명합니다. 설치한 릴리스의 `doklo generate --help`와 `doklo live-docs render --help`에서 옵션 제공 여부를 확인하세요.

## 실패한 문서만 복구하기

`generate`는 잘못된 JSON이나 잘린 모델 응답을 기본 한 번 더 시도합니다. `--retries 0`으로 끄거나 `--retries 2`로 최대 두 번까지 늘릴 수 있습니다. 재시도도 실행 동의와 토큰 한도에 포함되며 추가 사용량이 청구될 수 있습니다. 결과에는 시도 횟수·재시도 토큰·최종 실패 목록이 남습니다. 일부 실패는 성공 종료로 표시하지 않습니다.

토큰 한도 예약은 의도적으로 보수적입니다. 준비된 생성 호출 하나마다 프롬프트의 UTF-8 바이트 수에 출력 토큰 8,192개를 더하고, 이를 `retries + 1`만큼 예약합니다. 실행 동의 화면의 `utf8-bytes/4` 입력값은 표시용 추정치이고, 공급자가 보고한 사용량은 정산에 쓰는 실제 사용량입니다. 둘 다 보수적 한도 예약과는 구분됩니다. 승인된 배치는 해당 실행 동안 고정됩니다. 한도 때문에 일부 Dok이 미뤄지면 다음 실행에서 이미 생성된 Dok을 건너뛰고 나머지를 이어서 처리합니다.

```sh
doklo generate --only CHAT
doklo generate --only CHAT,CHILD --retries 0
```

기존 Dok은 기본적으로 건너뜁니다. 검토한 기존 문서를 다시 생성하려는 경우에만 `--only CHAT --force`를 명시하세요. 실패하면 기존 문서는 보존합니다. 실제 소스가 변경됐다는 오류는 같은 캐시로 재시도하지 말고 `doklo scan`과 `doklo consolidate`로 근거를 갱신한 뒤 다시 실행하세요. consolidate에는 모델 호출이 필요할 수 있습니다.

## draft를 검토용 화면으로 보기

출력 locale은 `--locale`, `DOKLO_LOCALE`, `en` 순서로 선택됩니다. 이 규칙은 번역 fallback chain의 첫 locale로 쓰이는 workspace `default_locale`과 별개입니다. 한국어 출력에는 `--locale ko`를 지정하세요. 한국어 draft 미리보기에는 안전 표시를 위해 영문 안내가 유지되고 한국어 안내가 함께 표시됩니다.

```sh
doklo live-docs render help-page --dok CHAT --format html --locale ko --preview
```

stable 템플릿의 Markdown·HTML 출력에 사용할 수 있습니다. 기본 경로는 `.doklo/output/preview/`이며 결과에 미검토 초안 표시가 들어갑니다. Hub의 상태·승인 이력은 바뀌지 않습니다. 일반 렌더의 검토 기준과 고객 문구 검사는 유지되므로 내부 용어 오류는 미리보기에서도 수정해야 합니다. 미리보기 결과를 정식 Publication의 게시·내보내기 근거로 사용할 수 없습니다.

## 생성 범위와 문구 검토

새 scan/consolidate는 스타일·자산·설정만으로 구성된 단위를 기능 문서 후보에서 제외하고, 보조 소스는 인벤토리에 남깁니다. 경로에 연결되지 않은 소스 후보는 별도 검토 대상으로 안내합니다. 이는 정적 import 기준 분류이며 동적 연결이나 프레임워크 연결 전체를 증명하지 않습니다. 기존 Hub 문서는 자동 삭제하지 않습니다.

Next.js에서 다른 화면의 공용 함수를 가져오면 필요한 선언·의존성·실행되는 모듈 초기화를 근거로 사용합니다. 전체 의존 파일은 변경 감지용으로 유지합니다. 예전 캐시는 `doklo scan` 후 `doklo consolidate`를 실행해야 이 근거 범위를 얻습니다. 기존 문서를 갱신할 때는 대상별 검토 후 `--only <ID> --force`를 사용하세요.

선택한 서비스 소스 루트의 `PRODUCT.md`·`VISION.md`가 scan 인벤토리에 있으면 제품 의도 근거로 함께 제시합니다. 상위 저장소나 예제·보관 폴더의 문서를 자동으로 가져오지 않습니다. 코드 근거와 제품 의도를 구분하며, 미구현 계획을 구현 사실로 쓰지 않도록 생성합니다.

모델이 보고한 범위 충돌·내부 구현 노출·근거 부족은 `_meta.content_review`에 남고, 우려가 있으면 CLI에 `CONTENT_REVIEW_REQUIRED`가 표시됩니다. `reported: false`는 모델이 검토 결과를 제출하지 않았다는 뜻입니다. 빈 우려 목록도 정확성 보증이나 승인을 뜻하지 않습니다. 고객 화면에는 내부 저장 방식 대신 사용자 행동과 결과가 적절하게 설명됐는지 검토하세요.

한국어 workspace에서는 설정한 합쇼체 또는 해라체에 맞춰 `intent`와 `outcome`을 완전한 문장으로 생성하도록 요청합니다. `intent`에는 행위자의 행동을 직접 쓰고, `outcome`에는 확인할 수 있는 결과를 씁니다. 따옴표 안 UI label, 정본 용어, 사실, 사람이 편집한 역할 이름은 그대로 유지해야 합니다. Doklo는 문장 끝을 기계적으로 바꾸지 않고 보수적인 문체 진단을 기록합니다. 충돌이 발견되면 일반 stable 렌더는 중단되고 draft 미리보기에는 경고가 남으므로, 원문을 잃지 않고 사람이 문장을 고칠 수 있습니다.

## 평가 점수 해석하기

`doklo evaluate`의 500점 만점 점수는 schema 형태, 고유 grouping, 비즈니스 표현 필드, 구조 완성도, 연결성을 측정하는 구조 점수입니다. 사실 근거, 현재 소스와의 최신성, 한국어 문체 품질, 사람의 승인을 점수에 포함하지 않습니다.

명령은 기록된 문체·모델 콘텐츠 검토 건수를 점수와 분리해 보여 줍니다. 콘텐츠 검토가 없음, 미보고, 보고됨, 형식이 잘못됐거나 알 수 없음인 상태와 현재 Dok lifecycle 건수도 구분합니다. 이 신호는 사람이 문구를 편집하기 전에 기록된 값일 수 있으며 새로 수행한 재평가가 아닙니다. 500/500, 기록된 우려 0건, 보고된 빈 검토 중 어느 것도 콘텐츠 승인을 뜻하지 않습니다. Dok 내용을 직접 검토하고 사람이 승인할 때까지 draft 상태를 유지하세요.
